What this branch adds
---------------------
PP foundation: PLE first-stage ownership checks and input preparation, empty
local attention groups, six-region cache planning/allocation and V2 model state.
Pinned-version compatibility: KV planning/builder imports, GDN parameter API
and lazy Medusa imports. No other model implementation or 310P/TurboQuant
caller changes are included. The Qwen-specific builder, draft markers,
metadata initialization and GDN replacement path are gated by Qwen4Exp
model configuration; non-Qwen models retain their original branch.
MTP WIP: target/draft cache ownership, metadata builder initialization and
per-batch draft token transport aligned with request IDs.
The base already provides the Qwen MTP model, proposer, PP engine patch and
FlashComm1 implementation. This branch adds no dedicated FlashComm1 kernel.
Graph replay is outside this eager validation scope.

MTP device validation
---------------------
1. Use only allocated, genuinely free cards. Verify process rows and HBM before
   launch; isolate code, container, selected devices, caches and ports.
2. Establish MTP off/on with PP=1 first, then PP=2. Keep the same weights,
   prompts, sampling parameters and workload. Record TP changes separately.
3. Start with V1, eager, synchronous scheduling and text-only requests.
   Control: --enforce-eager --no-async-scheduling
   --limit-mm-per-prompt '{"image":0,"video":0}'
   MTP adds: --speculative-config '{"method":"mtp","num_speculative_tokens":1}'
   Select the runner with VLLM_USE_V2_MODEL_RUNNER=0 or 1.
4. Save raw requests/responses and token IDs, draft/accepted metrics, per-worker
   logs, exit codes, layer partitions, effective configuration and model/source
   hashes. Exercise repeated requests and continuous Decode.
5. A successful startup or zero generated drafts is not a pass. Require actual
   speculation and output correctness against the control. Investigate TP-only
   effects before attributing differences to PP. Do not bypass the V2 QSA backend
   contract by relabeling it as another attention backend.

FlashComm1 Prefill device validation
-----------------------------------
Disable MTP to isolate the feature. Confirm the compatible communication
backend, expert parallelism, TP>1 and DP>1. Inspect the effective configuration
and execution evidence that sequence-parallel MoE/FlashComm1 actually runs.
TP4/PP2/DP1 on eight cards does not satisfy DP>1 and cannot prove this feature.
TP2/PP2/DP2 uses eight cards, but PLE first-stage capacity and layer partition
must be checked before launch. No final capacity-safe configuration is certified.
Once feasible, compare FlashComm1 off/on under the same parallel configuration,
with max_tokens=1 to scope the check to Prefill/first-token generation. Retain
first-token output, appropriate logits comparisons and actual communication
execution evidence. A flag that is silently disabled is not feature coverage.

Acceptance and reporting
------------------------
Report V1 and V2 independently as passed, unsupported with a concrete reason,
failed, or unverified. Startup, CPU-only tests and process exit are insufficient.
Do not claim full model accuracy or performance from short smoke requests.
Record the tested commit and environment so the receiver can reproduce results.
This WIP branch prepares continued testing; it is not a declaration that either
MTP+PP or FlashComm1 Prefill+PP is complete.
